# Phase 2 후속 개선·배포 상태 (2026-10-12)

주요 기능 및 기존 통합 루프 검증은 완료됐고 개선 코드도 Phase 2 전용 Docker에 적용했다. **모든 품질 기준 통과 상태는 아니다.** 반복 조회 성능 2개 조건과 아래 운영 제한을 남긴다.

## 이번 변경과 검증

- 탐지 로그 최대 256건을 Redis Stream 항목 하나로 전송한다. 기존 단건 형식도 읽으며 탐지 레코드/API 스키마는 유지한다.
- 로그 전용 `detection-redis`를 별도 생성했다. AOF + `appendfsync everysec`와 전용 볼륨을 사용하며 기존 캐시 Redis는 중단하거나 재생성하지 않았다.
- [영속화 검증](persistent-delivery-result.json): 새 Redis만 고정 ID로 강제 종료·재시작했고, fsync를 기다린 검증 항목이 보존됐다. 종료 직전 미반영 데이터까지 보장하는 검사는 아니다.
- [실제 Redis 검증](cache-stream-20261012-200207/results.json): 기존/묶음 형식으로 300건 전송, DB 일시 장애 재시도 후 고유 100건 저장, 잔여 0건. 캐시 무효화·TTL도 통과했다.
- [회귀 테스트](packed-pytest.txt): **192 passed, 1 skipped**, 기존 경고 3건. 실제 LLM 테스트 하나는 별도 실모델 검증 기록을 사용한다.
- [배포 확인](deployment-improved-result.json): admin-api/proxy/alerts 새 이미지 적용, 헬스 확인, dashboard·proxy 200, 탐지 저장, Slack 설정 및 정책 상태 보존. Phase 1 테스트 원본 17개 해시 일치.
- 실제 Slack observe/enforce 수신은 앞선 사용자 확인을 유지한다. 이번 배포 검증에서 추가 알림은 보내지 않았다.

## 최종 성능

[30초 측정 전체 표](load-packed-final-30s.md), [원본](load-packed-final-30s.json). 각 조건마다 클라이언트·프록시·관리 API·백엔드를 별도 프로세스로 실행했고, 측정 중 테스트·빌드·LLM 호출을 겹치지 않았다. 같은 Windows 호스트의 개발용 포화 부하 검사이며 운영 처리량 수치가 아니다. 부하 검증은 전용 검증 Redis(16382)로 실행했으며, 새 AOF Redis를 포함한 배포 구성 전체의 성능 측정은 아니다.

Phase 1은 대부분의 로그를 저장하지 못했으므로 두 버전의 저장 비용이 동등하지 않다. 이전 warm 100의 +57.12ms보다 차이가 줄었지만 warm 200은 +7.75ms에서 +11.00ms로 증가했다. 반복 측정으로 안정성이 입증된 개선율로 해석하지 않는다. cold 100은 p95가 낮아졌어도 처리량은 Phase 1 546.34 → Phase 2 426.27 req/s였으므로 모든 성능 지표가 개선됐다는 뜻도 아니다.

## 남은 작업·제한

1. **성능:** warm 100/200의 +5ms 기준 미달. 다음 검증은 배포와 같은 Linux/AOF 구성에서 프록시 처리·백엔드 대기·로그 저장 비용을 나눠 측정해야 한다. 기준을 바꾸거나 로그를 생략하여 PASS 처리하지 않았다.
2. **RAG 판단:** 기존 비교에서 조직 문서 경로가 tenant_match 대신 manual_review_required였다. 수동 검토 대상으로 유지하며 자동 분류 정답으로 계산하지 않는다.
3. **장애 내구성:** 프록시 메모리 큐의 강제 종료 손실, AOF의 최근 미반영 구간, Redis와 HTTP 저장 API의 동시 장애 손실 가능성, DB 장기 장애 시 Stream 적체 상한은 남아 있다. 이번 AOF 추가는 이 모두를 해결한 것이 아니다.
4. **실제 서비스 정책:** 현재 전용 실행 DB의 정책은 0개다. 배포 확인은 무정책 `/public/health`의 200/OBSERVE/미차단 로그 저장으로 수행했다. 기존 전체 정책·차단 통합 검증은 격리된 검증 DB에서 수행됐으며, 실제 적용 대상의 정책 생성·검토·승인은 별도다.
