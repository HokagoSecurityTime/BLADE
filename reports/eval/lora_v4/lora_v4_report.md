## 2. 질문별 결론

### Q1. v3가 v2보다 나은가 (같은 RunPod 환경, 3 seed)

- 주지표: v3b 0.338 ± 0.017 vs v2 0.299 ± 0.039. 차이 0.039는 v2 표준편차와 같은 크기라 **우열 인정 불가**(경계).
- manual 비율은 확실히 줄었다(38.1% → 19.6%, 차이 18.5%p ≫ 표준편차). v2의 과다 보류 문제는 v3b에서 해결됐다.
- 대가로 구체 정밀도가 떨어졌다(0.798 → 0.718). 보류하던 건을 구체 label로 답하면서 오답도 늘었다.
- owner_match F1은 상승(0.634 → 0.732, 차이 > 표준편차).
- v3a는 v2와 차이 없음. 쿼터 10%(v3b)가 25%(v3a)보다 낫다는 v3 보고서 결론은 그대로다.

### Q2. v4가 v3b보다 나은가

- 주지표 macro-F1: 0.356 ± 0.045 vs 0.338 ± 0.017. **차이 없음**(0.018 < 표준편차).
- 표준편차를 넘는 개선:
  - 구체 정밀도 0.718 → 0.855(+0.137). v2(0.798)보다도 높다. 구체로 답하면 맞는 비율이 가장 높은 모델이다.
  - owner_match F1 0.732 → 0.798.
  - 합성 포함 macro-F1 0.648 → 0.716.
  - oas 조건 합성 제외 0.403 → 0.463(v3b 표준편차 0.058과 비슷해 경계), v2 대비로는 확실히 높음.
  - 학습 출력의 검수 메타 문구 누출: test_v30 oas_code에서 v3a 20/20/36, v3b 37/26/30, v2 1/1/3 → **v4 0/0/0**. data-v3.1 정리가 효과를 냈다.
- 재현율은 0.603 → 0.632로 차이 없음. manual 비율은 19.6% → 28.6%로 다시 올라갔다(차이 9%p, 표준편차 약 4.5%p). v4는 v3b보다 보수적이지만 v2(38%)보다는 덜하다.
- 출력 오류: s42·s43이 각 7건. 원인은 rationale 도중 중국어로 전환되거나 같은 구절 반복으로 256토큰에 잘리는 경우다(예: "…경로·리소스 의미상寫在空白处…", "게시글·댓글·좋아요·팔로우·채팅·" 반복). v3b(1/3/5)보다 많고 s44는 0이라 seed 편차가 크다.

## 3. 종합

1. v4는 주지표 macro-F1에서 v3b와 통계적으로 구분되지 않는다. 대신 정밀도가 크게 올랐다(0.855). 학습 출력 오염(메타 문구)이 사라졌고, supp의 tenant_match를 처음으로 맞히기 시작했다. 현재 후보 중 가장 실용적인 모델은 v4다.
2. 남은 병목은 셋이다.
   - (a) owner_or_admin과 test_v30 manual은 support가 작고, 모든 모델이 0이다. 이 둘이 주지표 상한을 누른다.
   - (b) membership·owner_or_admin·tenant는 train 표본이 적다(5·8·33). supp에서 성능이 그 프로젝트 하나에 좌우된다.
   - (c) v4 출력 오류의 주원인은 중국어 전환과 반복이다.
3. 다음 실험 후보는 아래와 같다. 이번 결과로 test를 보고 고르는 것이 되므로, 실행 전 사용자 결정이 필요하다.
   - 출력 안정화: 디코딩 시 반복 패널티, 또는 JSON 제약 디코딩. 평가 설정 변경이라 모든 모델 재평가가 필요하다.
   - membership(그룹 지정 + 구성원 행 조회)·owner_or_admin(작성자 OR 관리자) 실제 코드 표본 보강. test_v31_supp 출처(Chatwoot·Chamilo·Flowise)와 그 포크는 쓰지 않는다.
   - 주지표 보조로 support ≥ 10 label만의 macro-F1을 함께 보고. 정의 추가라 eval-def 개정 승인이 필요하다.
