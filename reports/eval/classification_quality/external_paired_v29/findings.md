# 외부 비교 실험 최종 해석

## 결과

새 프로젝트 `fastapi/full-stack-fastapi-template`의 23개 엔드포인트를 같은 ID로 비교했다. 참조 라벨이 있는 19건에서 OAS 정적 투영본은 7/19(36.8%), OAS+코드는 15/19(78.9%) 일치했다. support가 있는 5종 macro-F1은 0.3091 → 0.6921이다. 7종 평균은 0.2208 → 0.4943이다.

이는 API 실행 전에 에이전트가 작성한 소스 검토 참조와의 일치율이다. 독립적인 사람 정답 정확도나 의도된 정책의 검증 완료를 뜻하지 않는다. 미확정 4건은 정답 보류로 대체하지 않고 점수 분모에서 제외했다. tenant와 그룹 membership 정답 사례가 없어 두 패턴의 성능은 아직 평가하지 못했다.

## 코드가 있어도 남은 불일치 4건

| 엔드포인트 | 참조 | 모델 | 문제 |
|---|---|---|---|
| DELETE /api/v1/users/me | manual_review_required | owner_match | 자기 계정만 삭제한다는 조건은 읽었지만, superuser는 자기 계정을 삭제할 수 없다는 추가 거부 조건을 놓쳤다. |
| DELETE /api/v1/users/{user_id} | manual_review_required | owner_or_admin | 관리자 필수 AND 자기 계정 삭제 금지를 소유자 OR 관리자로 바꿨다. |
| GET /api/v1/users/me | owner_match | membership_required | 토큰으로 확인한 현재 사용자 반환을 대상 그룹 구성원 검사로 오해했다. |
| POST /api/v1/login/test-token | owner_match | membership_required | 인증·활성 사용자 확인을 그룹 membership으로 오해했다. |

첫 두 건은 누락된 필수 조건 문제이고, 뒤 두 건은 입력에 없는 그룹 관계를 추론한 문제다. 기존 합성 실험의 문제가 실제 프로젝트에서도 나타났다. 이 분석을 이용해 이번 프롬프트·참조·예측을 수정하지 않았다.

## 검증기는 아직 외부 적용 불가

고정 검증기의 외부 코드/바인딩 평가 가능 건수는 0/23이다. 두 조건 모두 전부 적용 보류다. 올바른 구체 제안도 OAS 7/7, OAS+코드 15/15 보류됐다. 지원 표본의 오차단율은 N/A이고, 운영상 올바른 제안의 적용 보류율은 100%다.

metrics.json의 `independently_confirmed_unsafe=0`은 별도로 검사한 item 조회·수정·삭제와 user-by-id 네 경계에서만의 수치다. 전체 23건에 위험한 예측이 없다는 뜻이 아니다. 위 자기 삭제·관리자 삭제 불일치는 그 네 경계 밖에 있다. 위험 사례가 없는 제한된 감사 분모에서 검출률은 N/A이며, 모든 건을 보류했다는 사실을 위험 탐지 성공으로 계산하지 않는다.

## 실행과 재현

- API 응답 47회: 최종 예측 46건(23 × 2), 근거 인용 교정 요청 포함. 입력 87,862 / 출력 3,494토큰.
- 원본 함수·인가 의존성 로컬 검사 22건 통과. DB/사용자 객체 대역을 사용하며 실제 서버·JWT·PostgreSQL 통합 테스트가 아니다.
- 관련 pytest 27개 통과. 모델 원래 라벨과 원시 응답 보존.
- 프롬프트·검증기는 수집 전 해시 고정. 입력·참조는 API 실행 전에 고정. `preparation_initial/`, `preparation_precheck/`는 API 실행 전 수집 코드 검사 중 보존한 초안이며 실행에 사용한 입력이 아니다. 실제 입력은 execution_manifest.json의 해시로 식별한다.
- 기존 frozen test 253건 해시 유지. 런타임·학습 데이터·프롬프트·검증기 변경 없음.

## 다음 개발 과제

코드 제공은 도움이 됐지만, 현재 검증기는 실서비스 입력을 해석하지 못한다. 다음은 **외부 핸들러→인가 함수→객체 조회를 연결하고 조건을 보존하는 어댑터** 개발이다. 특히 NOT superuser와 target != caller 같은 부정 조건을 버리면 안 된다. CurrentUser를 그룹 membership으로 바꾸지 않는 바인딩 검증도 필요하다.

이번 프로젝트를 어댑터 개발에 사용하면 이후에는 개발셋으로 취급한다. 어댑터 버전을 고정한 뒤 다른 프로젝트에서 평가해야 한다. 현재 결과만으로 자동 정책 적용이나 6종 전체 성능을 주장할 수 없다.
