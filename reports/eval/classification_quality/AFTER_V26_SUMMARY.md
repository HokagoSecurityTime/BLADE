# v2.6 이후 진행 내용 정리

이 문서는 기존 실험 보고서와 저장된 결과를 정리한 것이다. 새로운 모델 실행이나 라벨 변경은 하지 않았다.

## 1. 전체 흐름

**사람 교정 예시를 넣은 v2.6 → 라벨 기준 정리 v2.7·v2.8 → OAS의 근거 부족 확인 → 코드와 실제 검사 조건을 연결하는 실험 → 제출 설계에 맞춘 v2.9 → 원래 LLM 라벨을 보존하는 적용 검증기 → 외부 코드 어댑터 개발·독립 평가** 순서로 진행했다.

핵심 설계는 유지했다. LLM이 6개 인가 패턴 또는 `manual_review_required`를 선택한다. 추가한 어댑터는 코드에서 검사 조건을 추출해 제안의 적용 가능성을 검토하며, LLM 라벨을 다른 라벨로 덮어쓰지 않는다.

현재까지 성능 향상이 일관되게 입증된 것은 아니다. 코드가 도움이 된 표본도 있지만, 새로운 프로젝트에서는 분류와 어댑터 모두 한계가 나타났다.

## 2. 버전 이름 구분

| 이름 | 무엇의 버전인가 | 역할 |
|---|---|---|
| 프롬프트 v2.6~v2.9 | LLM 분류 지침 | 고정 라벨 선택 기준 |
| 검증기 v1 | 적용 검증 실험 | 라벨이 필요한 조건을 누락하는지 검사 |
| 어댑터 v1·v2·v3 | 외부 코드 해석 모듈 | 핸들러·인가 함수·객체 조회 연결 |
| 각 보고서 폴더의 v1 | 개별 실험의 첫 버전 | 서로 다른 실험 식별 |

**어댑터 v1을 사용했다는 것은 프롬프트가 v1으로 되돌아갔다는 뜻이 아니다.** 최근 실험의 분류 프롬프트는 v2.9다.

## 3. v2.6: 사람 교정 예시 반영과 실패 원인 조사

### 변경

- v2.5 규칙 본문을 유지하고 가상 예시를 사람 교정 사례로 교체했다.
- 실제 검수 137건 중 교정 61건을 사용했다.
- 교정 61건을 few-shot 30건 / 검증 31건으로 분리했다.
- 200건 파일럿에서 검증 31건 일치율 60% 이상일 때만 전체 실행하도록 했다.

### 결과

- 검증 일치 **3/31, 9.7%**로 기준 미달이었다.
- 해당 승인 조건에 따른 전체 재라벨링은 중단했다.
- 불일치 28건을 분석하고, 데이터 근거 부족과 라벨 의미 충돌을 조사했다.
- 사람 교정·검증 61건의 설명·보안 정의를 보충했지만, 보충 자체를 성능 향상으로 간주하지 않았다.

## 4. 런타임 검증과 모델 분류 오류 분리

기존 베이스라인 점수가 낮은 이유를 모델 최초 판단과 후처리로 나눠 조사했다.

| 기존 설정 | 최종 macro-F1 | 정책 검증 후 보류로 식별된 건수 |
|---|---:|---:|
| GPT-4o-mini, RAG/controller on | 0.0903 | 26 |
| Qwen2.5:7b, RAG/controller on | 0.1222 | 22 |
| Qwen2.5:7b, RAG/controller off | 0.1874 | 6 |

이 표는 **v2.6~v2.9 분류 프롬프트 비교가 아니라 기존 런타임 v2.0 베이스라인 감사**다. 당시 원시 응답이 저장되지 않아, 최초 라벨의 F1이나 후처리로 잃은 정답 수는 복원할 수 없었다. 검증 보류 사례에는 ERD 누락 문제가 있었지만, 구체 라벨로 남은 오답도 많아 후처리만의 문제로 볼 수 없었다.

이후 평가 기록 보완·입력 근거 복구·소유권 처리 실험을 진행했다. 별도 SQLite/ASGI 소유권 실험에서는 생성자 바인딩, 본인 계정, 목록 쿼리 제한 등 의미 라벨과 실제 집행 방식이 다름을 확인했다. 이 검사는 분류 정확도 점수가 아니다.

자료: [런타임 감사](../runtime_validation_audit.md), [소유권 백엔드 실험](../ownership_backend_experiment.md).

## 5. v2.7: 통합 기준과 보류 허용

라벨 정의·판단 절차·근거·보류 규칙을 통합했다. 객체 ID나 설명이 있다는 이유만으로 구체 라벨을 강제하지 않고, ACL이나 독립 복합 조건을 한 라벨로 표현하기 어렵다면 보류하도록 했다. v2.6의 사람 교정 few-shot도 제거되어 여러 요소가 동시에 변경됐다.

동일 APIs.guru 100건 비교에서는 다음 변화가 있었다.

- `role_required`: **20 → 57건**
- `owner_match`: **24 → 2건**
- `manual_review_required`: **37 → 21건**
- 전체 라벨 변경: **59건**

보류 허용 범위를 넓혔는데 실제 보류는 감소했다. 이는 기준을 명확히 적는 것만으로 모델이 의도대로 따르지는 않는다는 신호였다. 당시 사람 정답이 없어 성능 개선으로 판단하지 않았다.

자료: [v2.6·v2.7 동일 100건 비교](v26_vs_v27_fresh100.md).

## 6. v2.8: 객체·권한 경계와 구현/의도 구분

외부 BOLA 연구를 설계 참고로 검토한 흐름에서, v2.7에 다음 구분을 추가했다.

- 대상 객체·행위, 요청자와 객체 관계, 실제 접근 조건을 분리한다.
- 구현된 검사와 명시된 의도된 정책을 구분한다.
- 코드 미확보를 검사 누락이나 public으로 해석하지 않는다.
- 인증과 역할, 관계 필드와 접근 조건, AND와 OR를 구분한다.
- BOLA 취약점 유형을 BLADE 정책 라벨에 그대로 대응시키지 않는다.

### 동일 100건 AI 검수 비교

| 버전 | AI 검수안과 일치 |
|---|---:|
| v2.6 | 39/100 |
| v2.7 | 23/100 |
| v2.8 | 25/100 |

이는 **v2.8 기준의 AI 검수안과 비교한 값**이다. 사람 정답 정확도가 아니다. 검수안의 88건이 보류여서 보류를 많이 낸 버전에 유리하고, 이를 모델 성능 순위로 일반화할 수 없다.

스펙만으로는 정책 근거를 확보하기 어렵다는 결론에 따라 코드가 있는 소스로 전환했다. 별도 소스 파일럿도 수행했지만, 근거 확보 범위가 제한돼 전체 표본 정확도로 취급하지 않았다.

자료: [v2.8 프롬프트](../../../training/data/prompts/policy_label_v2.8.md), [3개 버전 AI 검수 비교](ai_review_v26_v27_v28.md), [소스 파일럿](source_pilot/comparison.md).

## 8. v2.9: 제출 자료의 그룹 membership 의미로 정렬

사용자가 제출한 설계에 맞춰 `membership_required`를 **요청 대상 그룹·팀의 구성원 관계**로 정렬했다. 과거 프롬프트의 구독·플랜·등급 의미와 다르다.

- `tenant_match`: 요청자와 대상의 tenant 일치.
- `membership_required`: 요청자가 대상 그룹의 구성원.
- 두 조건이 독립적으로 모두 필요하면 하나를 버리지 않는다.
- 구독 등급만 요구하는 정책은 새 6종으로 표현되지 않으면 보류한다.
- 최종 라벨 선택은 여전히 LLM이 수행한다.

기존 런타임의 membership 등급 비교는 대상 그룹 구성원 조회가 아니다. 따라서 새 의미의 라벨을 기존 런타임에 자동 적용하지 않았다.

### v2.9 개발 실험

| 실험 | 결과 | 해석 |
|---|---|---|
| 그룹 정책 합성 8건 | v2.8 5/8, v2.9 7/8 | 새 기준 적합성 비교. 과거 기준의 정확도 비교 아님 |
| 경계 사례 30건: 코드 | 21/30 | 15개 정책 × 문법 변형 2개 |
| 같은 30건: 코드+추출 조건 | 15/30 | 추출 조건을 프롬프트에 넣는 것만으로 개선되지 않음 |

복합 조건을 구체 라벨 하나로 축약하는 오류가 남았다. 그래서 조건 추출을 단순한 프롬프트 보강 외에 **자동 적용을 차단하는 별도 검증**에 사용하기로 했다.

자료: [v2.9 프롬프트](../../../training/data/prompts/policy_label_v2.9.md), [그룹 정책](group_policy_v29/report.htm), [30건 경계 실험](boundary30_v29/report.htm).

## 9. 원래 LLM 라벨을 보존하는 적용 검증기

LLM label·confidence는 그대로 저장하고, 별도 검증 결과에 다음을 기록했다.

- 제안은 허용하지만 실제 코드 조건은 거부하는 상태: 필수 조건 누락 또는 허용 확대.
- 실제 코드는 허용하지만 제안은 거부하는 상태: 과도한 제한.
- 코드·바인딩 미확보: 평가 불가 및 보류.
- 의미 동등성 통과와 실제 자동 적용 승인은 별개.

기존 합성 30건을 재사용했을 때 코드 입력 결과에서 조건 누락 7건, 코드+조건 입력 결과에서 13건을 탐지했다. 각각 올바른 구체 라벨 12건의 오차단은 없었다. 다만 합성 개발셋 결과다.

자료: [적용 검증기 실험](application_guard_v1/report.htm).

## 11. 최신 독립 프로젝트 평가

어댑터·프롬프트 해시를 고정한 뒤, 기존 개발에 사용하지 않은 **fastapi-users 사용자 라우터 전체 5건**을 평가했다. 평가 중 어댑터는 수정하지 않았다.

| 지표 | OAS 정적 투영본 | OAS+코드 |
|---|---:|---:|
| 에이전트 소스 검토 참조 일치 | 0/5 | 1/5 |
| macro-F1, support 있는 2종 | 0.0000 | 0.2500 |
| 어댑터 완전 분석 | 0/5 | 0/5 |
| 어댑터 부분 분석 | 0/5 | 0/5 |

이 프로젝트는 인증 의존성을 함수 내부에서 동적으로 생성한다. 고정 어댑터가 인자→생성된 의존성→실제 인가 검사까지 연결하지 못해 모두 보류했다.

원본 인증 함수의 로컬 허용·거부 검사 8건, 관련 pytest 53개는 통과했다. 이는 실제 DB/JWT/HTTP 통합 검증이나 모델 정확도 검증과 다르다. 추가 API 응답 10회, 입력 24,546 / 출력 730토큰을 사용했다.

새 프로젝트라 하더라도 표본 5건·라벨 2종뿐이며, 기본 라이브러리 구성에 대한 에이전트 참조다. 전체 6종 또는 실제 배포 성능으로 일반화할 수 없다.

자료: [독립 프로젝트 보고서](adapter_v3_holdout/report.htm), [상세 지표](adapter_v3_holdout/metrics.json).

## 12. 현재 상태와 남은 과제

### 완료한 것

- v2.6 이후 라벨 기준·프롬프트 비교와 원인 분석.
- OAS만 있는 입력의 한계를 확인하고 코드 기반 비교 실험 수행.
- 그룹 membership 의미로 v2.9 정렬.
- 원래 LLM 라벨과 별도 적용 검증 결과를 분리.
- 외부 핸들러·조회 연결 및 조건 보존 어댑터 개발.
- 고정 버전으로 새 프로젝트 평가, 실패 결과까지 보존.

### 아직 완료하지 않은 것

- 임의 프로젝트에 통하는 범용 인가 호출 그래프 분석.
- 동적 의존성 factory의 인자 전달·반환 함수 조건 추적.
- 전체 6종을 포함한 충분한 독립 정답셋 평가.
- 실제 배포의 DB/JWT/사용자 정의 callback까지 검증한 정책 집행.
- 새 그룹 membership 의미를 지원하는 런타임 집행.

### 현재 결론

**분류 프롬프트만 수정해서 해결되지 않아 입력 근거와 적용 검증을 보강해 왔다. 개발 사례에서는 작동하지만, 독립 프로젝트로 옮기면 아직 분류와 코드 연결 모두 약하다.**

다음 기술 과제는 동적 의존성 factory 추적이다. 이번 독립 프로젝트를 그 개발에 활용하면 해당 데이터는 이후 개발셋으로 취급하고, 다음 독립 평가는 다른 프로젝트에서 해야 한다.

기존 frozen test 253건과 이전 결과는 보존했다. 최근 어댑터 실험에서 모델 학습·운영 정책 자동 활성화·런타임 변경은 수행하지 않았다. `semantic_candidate_pass`는 의미 검증 결과이며, `auto_apply_allowed`는 계속 false다.

## 13. 수치를 읽을 때 주의할 점

- **사람 검수 일치, AI 검수 일치, 합성 계약 일치, 소스 검토 참조 일치**는 서로 다른 지표다.
- 서로 다른 표본과 라벨 기준의 점수를 하나의 성능 추이로 연결하지 않는다.
- 테스트 통과 건수는 구현 검증이며 분류 정확도가 아니다.
- 모든 요청을 보류하면 안전하게 막을 수 있지만, 그것을 위험 탐지율 100%로 계산하지 않는다.
- 지원 표본이 0이면 탐지율·오차단율은 0%가 아니라 계산 불가(N/A)일 수 있다.
- 현재 어떤 버전이 모든 데이터에서 가장 좋다고 결론 내릴 근거는 없다.
